Why modal mu-calculus for behaviours

25 MAY 2026 · STEWART MACKENZIE

Non-determinism is the enemy. Every bug in a distributed system, every race condition, every heisentest — they all trace back to the same root cause: the system entered a state the programmer didn't anticipate because something happened in an order they didn't predict. The goal of any serious systems language is to make things deterministic, and when they can't be deterministic, to return to determinism as fast as possible.

This is the design principle behind Munu's behaviour clause, and it's why we chose modal mu-calculus as the language for writing it.

The non-determinism problem

A single process running in isolation is deterministic. Give it the same input, it produces the same output. The trouble starts the moment you have two processes. Now you have messages, and messages arrive in some order, and that order depends on scheduling, network latency, load, cosmic rays — things outside your control.

If you don't know the order messages arrive in, your system is non-deterministic. If you do know the order, it's deterministic. This is the fundamental divide. A scheduler that enforces ordering is a determinism machine. A protocol that tolerates arbitrary ordering is a concession to non-determinism.

Erlang understood this. The entire OTP philosophy — fail fast, let it crash, restart from a known good state — is a strategy for returning to determinism quickly. When a process enters an unpredictable state, don't try to recover. Kill it. Restart it. Begin from a state you understand. The supervisor is not error handling — it's a determinism recovery mechanism.

Where Erlang hits the ceiling

OTP's supervisor restart strategies are an enum: one_for_one, one_for_all, rest_for_one, simple_one_for_one. Four options. That's it.

These four cover a surprising number of cases. But they are fundamentally fixed responses to a single event type — a child process died. They can't express:

— "Restart this child, but only if it crashed twice within 10 seconds — otherwise escalate."
— "If child A fails, restart B and C but not D, because D holds state that A depends on but B and C don't."
— "Wait for acknowledgement from a quorum of three out of five replicas before considering a write committed."
— "If two children fail simultaneously, that's a different situation than if they fail sequentially."

Hardened Erlang programmers write these patterns. They do it with nested supervisors, custom gen_servers that implement their own restart logic, state machines that track failure counts, and careful message passing between supervisor levels. It works — but it's ad-hoc, implicit, and unverifiable. The logic is spread across multiple modules. No tool can check that the quorum protocol is correct.

The scheduler question

Here's the insight that led us to modal mu-calculus: a behaviour clause is a scheduler specification. It tells the runtime what to do when events happen. Process A sent a message. Process B crashed. A quorum was reached. A timeout fired. The behaviour is a formula that matches events and prescribes actions — exactly what a scheduler does.

So the question becomes: what's the best language for writing scheduler specifications?

You need something that can talk about sequences of events over time — not just "what happened" but "what happened, and then what happened next, and what must always eventually happen." You need fixed points — the ability to say "this pattern repeats forever" (the nu operator) or "this pattern eventually terminates" (the mu operator). You need modalities — the ability to say "after observing event X, action Y must be possible."

Modal mu-calculus has all of this. It's the most expressive temporal logic in the linear-time/branching-time hierarchy. It subsumes CTL, CTL*, LTL, and Hennessy-Milner logic. It is exactly the right tool for the job.

And here's the thing that made the decision easy: LLMs already know it. Modal mu-calculus appears in hundreds of papers, textbooks, and verification tool manuals. When you ask an LLM to write a behaviour formula, it can reason about it. It can check it. It can generate counter-examples. This is not true of ad-hoc Erlang supervisor trees.

What it looks like

An Erlang supervisor restart strategy is a single atom:

Erlang

one_for_one — if a child dies, restart just that child. No conditions, no sequencing, no memory of prior failures.

Munu

nu X. [fail(self, _)] <restart(self)> X and [_] X — observe events forever. If a fail event from self is observed with any reason, a restart action must be available, and then continue observing. For all other events, continue observing.

They look similar for the simple case. The power shows up when you need something the enum can't express.

Two strikes and escalate

Restart on first failure. Escalate on second failure. In Erlang this requires a custom supervisor with state tracking. In Munu:

do: nu X. [fail(self, _)] <restart(self)> nu Y. [fail(self, _)] false and [_] Y and [_] X

One formula. Two fixed-point variables. The outer loop (X) handles the first failure by restarting and entering the inner loop (Y). The inner loop treats a second failure as a violation (false) — which propagates up to the parent supervisor. No state variables, no failure counters, no message passing.

Quorum

Wait for acknowledgement from a majority before proceeding. In Erlang, this is a gen_statem or a custom process with careful bookkeeping. In the mu-calculus, a quorum over three replicas is a nesting of diamond modalities — each <ack(replica_n)> demands that an acknowledgement from that replica is reachable, and the nesting structure specifies how many must be observed before the formula is satisfied.

What took a hundred lines of Erlang — state machine, message handlers, timeout logic, edge cases for late arrivals — collapses into a formula that a model checker can verify and an LLM can read.

Determinism recovery

The deeper point is not that mu-calculus is more expressive than an enum. It's that mu-calculus formulas are specifications of how to return to determinism.

When a process crashes, the system has entered a non-deterministic state — you don't know what the process was doing when it died, what messages were in flight, what partial state it left behind. The behaviour formula specifies the path back to a known state. Restart from the last checkpoint. Wait for a quorum to agree on the current state. Escalate to a supervisor that has a wider view of the system.

Every one of these is a temporal property — something that must eventually happen, or something that must always hold. Temporal properties are what modal mu-calculus was invented to express. We're not forcing a formalism onto a problem. We're using the formalism that was designed for exactly this problem.

The behaviour clause doesn't handle errors. It specifies the contract between a process and its supervisor for maintaining determinism in the presence of failure.

The must clause

There's a second half to every behaviour: the must: clause. If do: specifies what the supervisor does when events happen, must: specifies what the supervised process is obligated to do. It's the process's side of the contract.

A must: clause that says true imposes no obligation — the process can do anything. A must: clause that says nu Y. [fail(self, _)]~fast_response <restart(self)> Y says: if this process fails, it must fail within the timing envelope defined by fast_response, and it must be restartable. The tilde (~) attaches a timing CDF — a probabilistic deadline.

This is where behaviour formulas go beyond anything OTP can express. OTP supervisors don't constrain the behaviour of the supervised process — they only react to its death. Munu's must: clause lets you write obligations that the supervised process must satisfy, and the compiler can verify that the process's implementation is consistent with those obligations.

Why not just write code

You could write all of this as regular code. Erlang developers do, every day. But there's a critical difference: code is opaque to analysis. A custom supervisor written in Erlang is a program that happens to implement a supervision strategy. A behaviour formula is a specification of a supervision strategy.

The formula can be model-checked. The formula can be composed — two behaviour formulas can be merged and the result checked for contradictions. The formula can be read by an LLM and translated into natural language. The formula can be compared to the actual process trace at runtime and violations reported immediately.

None of this is possible when the supervision logic is "a gen_server with some state." You've lost the structure. You've lost the ability to reason about it. You've traded determinism for flexibility, and in distributed systems, that trade always costs you eventually.

The formal connection

Modal mu-calculus extends Hennessy-Milner logic with least (μ) and greatest (ν) fixed points. The box modality [a] means "for all transitions labelled a" — a universal quantifier over events. The diamond modality <a> means "there exists a transition labelled a" — an existential quantifier. The fixed points add recursion: ν X. φ(X) defines the greatest fixed point of φ, which captures "φ holds forever" — liveness. μ X. φ(X) defines the least fixed point, capturing "φ eventually holds" — termination.

This gives behaviour formulas exactly the right expressive power for supervision: "always eventually restart" is a ν-formula wrapping a μ-formula. "Never allow two consecutive failures without escalation" is a ν-formula with nested branching. The alternation depth — how many times μ and ν nest inside each other — corresponds directly to the complexity of the temporal property being expressed.
