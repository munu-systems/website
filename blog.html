The mu/nu duality

25 MAY 2026 · STEWART MACKENZIE

Every programming language secretly has two kinds of computation in it. One kind builds a finite value and stops. The other kind observes an infinite process and never stops. Most languages hide this distinction entirely. Munu makes it the foundation of the language.

Two kinds of computation

Think about the simplest programs you write. A function that doubles a number takes an input, produces an output, and terminates. It builds something finite. We call this mu.

Now think about a server. It accepts a request, responds, and waits for the next one. It doesn't terminate — termination is a bug. It observes an infinite stream of events. We call this nu.

Every non-trivial system has both. A web server (nu) calls a request handler (mu). A sensor loop (nu) reads a temperature (mu). A supervisor (nu) restarts a failed process (mu).

The question is whether your language knows the difference.

What Erlang got right

Erlang is the closest any production language has come to making this split explicit. A gen_server's handle_call is a finite computation — receive a message, compute a reply, return. The gen_server loop itself is infinite — it calls handle_call forever. OTP's supervisors compose these infinite processes into trees.

But Erlang never names the duality. The infinite loop is just tail recursion. The finite handler is just a function. There's no syntactic or type-level distinction between "this function terminates" and "this function runs forever." The nu operator is there — it's just implicit, buried in recursive calls and OTP conventions.

This works. Erlang has powered telecom switches for decades. But the implicit nu constrains what you can do with it.

What happens when nu is explicit

When the language knows that a computation is infinite — not by convention, not by pattern, but by declaration — three things become possible that are impossible otherwise.

1. Hot code swapping becomes principled

If the compiler knows which computations are infinite, it knows exactly where to inject new code. An infinite process has a well-defined observation boundary — the point where it yields and waits for the next event. That's where you swap. Erlang does this through careful convention and runtime magic. When nu is a language construct, the compiler can verify that a hot swap is safe before it happens.

2. Supervision becomes a type, not a pattern

In Erlang, a supervisor is a behaviour — a convention enforced by OTP callbacks. In Munu, a contract is a language construct that composes infinite processes. The behaviour clause specifies what happens when a child process fails: restart it, escalate, or let it die. This isn't a convention the programmer must follow — it's a formula the compiler verifies.

3. You can put logic on the infinite

This is the big one. Once you can name and compose infinite processes, you can attach verification logic to them. A behaviour clause is a formula over the infinite — it specifies what must always be true of a process that never terminates. A value logic clause proves properties about the finite computations inside. A privacy logic clause controls what information flows where.

None of this is possible when the infinite is just recursion. You can't attach a type to "calls itself forever." You can't verify a property of "the thing inside the loop." You need the nu operator to be explicit for the compiler to reason about it.

Contracts compose the infinite. The infinite composes the finite. The finite is where the work happens. The contract is where the guarantees live.

The contract as composition

A Munu contract is not a class, not a module, not an actor. It's a composition point for the mu/nu duality. The contract body spawns infinite and finite computations. The behaviour clause governs what happens when they fail. The value logic clause governs what properties their outputs must satisfy.

This is what "contracts compose the infinite" means concretely. A contract can spawn other contracts. Each one supervises its own tree of mu and nu computations. The supervisor tree emerges from the language, not from a library.

And because contracts are explicit compositions of mu and nu, they're reusable. A contract is a unit of deployment, verification, and hot-swap. You can move it from an MCU to a server. You can upgrade it at runtime. You can prove properties about it at compile time. None of this works if the infinite is hidden inside recursion.

Why this matters for LLMs

LLMs are good at finite computation. Ask one to write a function that parses a date, sorts a list, or computes a hash — it will probably get it right. Ask it to write a correct concurrent server and it will hallucinate race conditions, forget edge cases in error handling, and produce something that passes a few tests but fails in production.

The mu/nu split helps because it separates what LLMs are good at from what they're bad at. The LLM writes mu functions — finite, verifiable, bounded. The contract structure — which nu processes to spawn, how to supervise them, what invariants to maintain — is where the human (or a more capable system) applies judgement. And the compiler verifies both.

For the categorically inclined

The names are not accidental. mu (μ) is the least fixed point — the initial algebra. It builds finite structures by induction: natural numbers, lists, trees. A mu function always terminates because the structure it builds is finite.

nu (ν) is the greatest fixed point — the final coalgebra. It observes infinite structures by coinduction: streams, servers, interactive processes. A nu function never terminates because the structure it observes is infinite.

The duality between initial algebras and final coalgebras is one of the deepest in computer science. Most languages collapse it. Munu makes it a first-class construct — not because category theory is the point, but because the programming model that falls out of the duality is exactly what fault-tolerant distributed systems need.
